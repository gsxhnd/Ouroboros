# 02 - 架构设计

## 整体架构

```text
┌────────────────────────────────────────────────────────────┐
│ React Sync Task UI                                         │
│ shadcn/ui + Zustand + i18next                              │
│ 只访问 Ourboros typed API，不直连 rclone RC                │
└───────────────────────────┬────────────────────────────────┘
                            │ 同源 HTTP / SSE
┌───────────────────────────▼────────────────────────────────┐
│ ourboros (Go HTTP + desktop shell)                            │
│ bridge: HTTP 路由 / JSON / SSE / 静态 UI；桌面托盘进程内调用  │
│ service: 传输无关用例、跨存储校验与编排、事件发布             │
│ domain: 工作区/设置存储、rclone 管理、同步调度、mount 监管    │
└───────────────┬───────────────────────────┬────────────────┘
                │ typed API / 受限 RC client │ 子进程
┌───────────────▼───────────────┐  ┌────────▼─────────────────┐
│ rclone rcd                    │  │ rclone mount             │
│ 回环地址 + 临时凭据           │  │ 受监管的挂载进程          │
└──────────────────────────────┘  └──────────────────────────┘
```

Go 服务是唯一可信控制面。React 不知道 RC 地址和凭据，也不直接执行系统命令。所有路径、remote 名称、同步方向、危险操作和状态转换都由服务端校验。

## 进程与模块

```text
ourboros
├── CLI / server / desktop       # 组装与生命周期
├── bridge
│   ├── HTTP router / SSE        # internal/httpapi，仅传输职责
│   └── desktop tray             # 进程内调用 service
├── application service          # internal/service，用例校验与编排
├── application state            # domain 容器与组装根
│   ├── RcloneSupervisor
│   ├── WorkspaceStore
│   ├── SyncScheduler / JobStore
│   └── MountSupervisor
├── domain
│   ├── workspace
│   ├── remotes / files
│   ├── sync
│   ├── mounts
│   └── settings
└── static web handler
```

`internal` 提供传输无关的 `service` 用例层、rclone RC 客户端、进程监管、HTTP bridge、CLI 和持久化。HTTP handler 与桌面托盘都通过 `service.Services` 调用用例；`service` 不依赖 `net/http`，domain store 不被 bridge 直接操作。前端业务类型必须与 API 契约对应，不在组件内拼装 RC 请求。

## 单一二进制与运行模式

| 子命令 | 用途 |
|--------|------|
| `ourboros server` | HTTP 服务、Web 静态资源、rclone 和业务任务 |
| `ourboros version` | 打印版本 |

`server` 支持两种 rclone 会话：

- 托管模式：Ourboros 选择可执行文件、生成临时 RC 凭据、启动 `rclone rcd` 并监管子进程。
- Attach 模式：连接用户已启动的 RC；Ourboros 不拥有外部进程，stop 只断开会话。

## 请求与事件流

1. 浏览器读取 `/api/sync/tasks` 和系统状态。
2. 用户创建或修改同步任务，HTTP bridge 解码请求，`service` 校验并编排用例，domain store 原子写入 workspace JSON。
3. 手动同步或计划调度创建 job；任务调用受限 rclone RC 操作（含任务上保存的限速与大小上限）。
4. 服务通过 SSE 发送任务/挂载状态；浏览器断线后先拉取快照，再指数退避重连。
5. mount 由服务启动并监管独立子进程，状态与退出原因通过 API/SSE 暴露。

## 信任边界

- 浏览器只访问 Ourboros 同源 `/api`。
- RC 只监听 `127.0.0.1`，使用启动时生成的临时凭据。
- RC URL、RC 凭据、remote token 和 `config/dump` 不通过 API 返回，也不落盘。
- `POST /api/rc/{command}` 仅允许明确 allowlist 命令；业务操作优先使用 typed API。
- Ourboros 默认只绑定 `127.0.0.1`。需要局域网 / Docker 访问时配置 `--auth-token`（env `OURBOROS_TOKEN`）：所有 `/api` 请求必须携带 Bearer token，跨源 Origin 被拒绝。对外发布前仍需补齐 TLS 与完整 CSRF 防护。

## Web UI 托管

前端构建产物 `web/dist` 不 embed 进二进制，查找顺序为：

1. CLI `--webui` / `--web-dir`
2. `OURBOROS_WEB_DIR`
3. 可执行文件旁的 `web/`

显式指定的目录必须包含 `index.html`，否则拒绝启动。未指定且找不到 UI 时仍启动 API-only 服务。开发使用 Vite `:1420` 代理到后端 `127.0.0.1:8080`。

## Monorepo 目标结构

```text
Ourboros/
├── cmd/
│   ├── ourboros/          # 无界面服务，用于本机、Docker 和 Linux
│   └── desktop/           # Wails 窗口，打开同一个 HTTP 服务
├── internal/              # rclone、任务、存储和 HTTP
├── web/                   # React Sync UI
└── docs/dev/              # 产品、接口和实施文档
```
